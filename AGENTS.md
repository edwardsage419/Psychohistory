# Psychohistory Archive Operating Guide

## Repository status

Psychohistory is `ARCHIVED_INACTIVE`.

Read `CURRENT_STATE.md` and `docs/PROJECT_ARCHIVE_2026_09_11.md` before any substantive action.

There is no active development task in this repository.

## Default behavior

When asked to continue Forecast Trust, Forecast Ledger, model audit, failure corpus, or related successor work, do not implement it in Psychohistory by default.

Use `docs/NEW_PROJECT_MIGRATION_PACKET.md` as predecessor design input for the separate successor project.

When asked to inspect Psychohistory, restrict work to the historical question actually asked.

## Allowed archive activity

Without reactivation, allowed work includes:

1. reading repository files
2. auditing accepted historical work
3. reproducing existing results and tests
4. citing historical evidence
5. exporting or reviewing migration material
6. checking repository preservation integrity

Critical preservation repair requires explicit authorization and must preserve historical meaning.

## Prohibited active development

While the repository remains archived, do not begin or resume:

1. Forecast Trust Core implementation
2. Forecast Ledger Genesis
3. new prospective forecast issuance
4. GKG recovery
5. independent semantic review
6. indicator promotion
7. new source family integration
8. scoring or calibration development
9. frontend or API development
10. production workflows or recurring infrastructure

Historical files describing these activities remain provenance and design records. They are not execution authorization.

## Scientific preservation

Do not modify accepted scientific evidence, frozen sample membership, machine identity states, human review provenance, evidence sufficiency classifications, failed records, unresolved records, or historical reports merely to simplify the archive.

`SCIENTIFIC_INVARIANTS.md` remains authoritative for historical scientific interpretation.

Missing evidence remains missing. Archiving creates no new scientific conclusion.

## Successor migration boundary

Reusable methodology is distilled in `docs/NEW_PROJECT_MIGRATION_PACKET.md`.

The successor project starts from a clean repository and independently owns its future schemas, code, forecasts, anchors, resolutions, evaluations, and failure records.

Psychohistory artifacts may be referenced as predecessor provenance. They do not automatically become native successor evidence.

## Reactivation

Psychohistory can be reactivated only through a new explicit owner decision recorded in the repository.

That decision must state why the proposed work belongs in this historical repository rather than the successor project and must define a bounded task before implementation begins.

A request to inspect, reproduce, cite, or reuse historical material does not reactivate the project.
