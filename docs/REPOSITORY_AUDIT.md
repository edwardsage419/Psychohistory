## Validator review and intended changes

The baseline checks only eight columns, never validates dates, decodes with
replacement, and uses CSV quote semantics for a line-oriented TSV format.
Discovery happens outside its exception handler; failures have no JSON artifact.
ZIP cardinality rejects multiple data members but CRC/encoding/resource failures
need fixtures and stable error codes. Timestamped runs and insertion-order ties
need explicit reproducibility rules. The date CLI flag does not select a date.

Implement strict documented GKG 2.1 structure, preserve empty fields, calendar
validation including documented unknown-date sentinel, bounded ZIP processing,
per-row rejection counts, stable full frequency counts, content hash and source
reference. Fail closed on decoding/ZIP errors; partial statistics must be labeled.
Separate offline validation from opted-in network acquisition. Add atomic reports
for acquisition and validation failures. Introduce versioned report, source and
observation contracts with deterministic offline tests and no topic mappings.

Acceptance: offline tests pass; fixed inputs/metadata yield identical JSON;
operational failures have codes; dashboard/runtime/data remain byte-identical;
no generated bytecode tracked; GKG recommendation distinguishes verified facts,
local integration results and unresolved production gates. Main is not merged.

Risk: stricter checks can reject batches previously accepted. This is intentional
in an isolated validator; reports preserve evidence for investigating rejection.
